# DVC Mallorca spike — Issue #339

This directory is a deliberately isolated experiment. It does not import or call
the current YACS asset library, downloaders, world generation, runtime code or
Unreal Content. Its only purpose is to answer whether DVC can manage one real
Mallorca terrain source through:

```text
official CNIG WCS source
  -> DVC import/cache
  -> isolated local DVC remote
  -> remove working copy and local cache
  -> DVC pull/rehydrate
  -> deterministic prepare stage
  -> store/reuse derived outputs
  -> forced byte-identical reproduction
```

## Boundaries

- The source is a bounded ~1 km CNIG/IDEE MDT05 sample from Mallorca.
- Raw and prepared bytes are ignored by Git and owned by this nested DVC repo.
- `.dvc-storage/` is a local proof remote, not a proposed production location.
- The prepared float32 heightfield is experimental and never enters `Content/`.
- The sample is not route, physics, terrain or production-manifest authority.
- No current downloader or `scripts/assets/yacs_asset_library.py` is changed.

## Prerequisites

- Git
- `uv` 0.11 or newer
- network access to PyPI and the declared CNIG WCS URL for the initial run

The environment is locked in `uv.lock`. DVC, NumPy and Rasterio are scoped to
this directory and are not added as production project dependencies.

Experimental tool provenance:

| Package | Version | License | Use |
|---|---:|---|---|
| DVC | 3.67.1 | Apache-2.0 | data cache, remote and pipeline orchestration |
| NumPy | 2.2.6 | BSD-3-Clause | deterministic raster array conversion |
| Rasterio | 1.4.3 | BSD-3-Clause | bounded GeoTIFF read and resampling |

The packages are resolved from PyPI by `uv`; no third-party source or wheel is
vendored or redistributed in Git.

## Run the complete proof

From this directory:

```powershell
uv sync --locked
uv run python -m unittest discover -s tests -v
uv run python run_spike.py
```

`run_spike.py` performs the destructive part only inside this experiment. It
removes `data/raw/mallorca_mdt05.tif`, the two prepared outputs and this nested
repo's `.dvc/cache`, then requires DVC to restore them from `.dvc-storage/`.
The proof fails if the source SHA-256 changes or any prepared output differs.

The machine-readable result is written to ignored
`evidence/latest-run.json`. DVC's reproducibility identity is committed in
`dvc.lock`; the preparation report additionally records SHA-256 for the source,
the prepared bytes and the YACS-facing artifact fingerprint.

## Manual DVC stages

The runner is equivalent to the following high-level sequence:

```powershell
uv run dvc update data/raw/mallorca_mdt05.tif.dvc
uv run dvc push data/raw/mallorca_mdt05.tif.dvc
# remove the working file and this nested repo's .dvc/cache
uv run dvc pull data/raw/mallorca_mdt05.tif.dvc
uv run dvc repro
uv run dvc push
# remove prepared outputs and this nested repo's .dvc/cache
uv run dvc pull
uv run dvc repro --force
uv run dvc status
```

## Provenance

The source contract is in `source.json`. The provider is Spain's Centro
Nacional de Informacion Geografica (CNIG/IDEE); the dataset is the 5 m Digital
Terrain Model for the Iberian Peninsula and Balearic Islands. The catalog lists
CC BY 4.0. Raw bytes are cached locally by DVC and are not committed to Git.

## Executed result — 2026-10-03

The complete cycle passed on Windows 11 with DVC 3.67.1 and Python 3.12.10:

| Check | Result |
|---|---|
| official source import | 99,090-byte GeoTIFF, 222 x 222, EPSG:4326 |
| source SHA-256 | `4adfe1be1f4a6751b9376168292e82317da8cdbe0641d81c003aa2b7355fd87a` |
| raw delete + cache delete + pull | restored with the same SHA-256 |
| prepared remote reuse | heightfield and report restored byte-identically |
| forced `dvc repro` | heightfield and report regenerated byte-identically |
| artifact fingerprint | `cc8b4ea81b320913f16d1ba345505209371350ae5c6f69dde4ff46f21cddf08c` |
| heightfield SHA-256 | `ded33fb407b1a6a6a6f73c84c98f85987324f64d053c697efa2f0f96467ade92` |
| final status | `Data and pipelines are up to date.` |

The Windows hardlink cache marks DVC objects read-only. The runner therefore
removes that attribute only while deleting the already-validated nested
`.dvc/cache` directory. It refuses to delete any path outside this spike root.

DVC's committed descriptors and local object database use MD5 identities for
this filesystem remote. The spike therefore does **not** claim that DVC's
internal object key is SHA-256. `source.json` and `prepare.py` add the required
auditable SHA-256 source check and YACS-facing artifact fingerprint. A future
production decision under #339 must keep that thin verification layer if
SHA-256 remains a project requirement.

## Decision boundary

This spike can demonstrate DVC mechanics, but it does not approve a production
remote, define the future `yacs assets` CLI, migrate existing providers or
replace Git LFS/Zen DDC. Those remain follow-up decisions under #339.

Technical conclusion: DVC satisfies the tested register/store, local-remote
deduplication, remove/rehydrate, dependency invalidation, prepared-output reuse
and deterministic reproduction needs. It is a viable storage/pipeline engine
for the next #339 design step, provided YACS keeps project policy, provenance,
profiles and SHA-256 verification in a thin layer above DVC.
